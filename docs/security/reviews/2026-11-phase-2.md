## 6. Findings

Severities follow the CVSS 4.0 rating. Every finding is scored for the
planned app, which renders documents on open. Exploitation needs a user who
opens a crafted document. No released version was affected.

### SR-2026-001: Small documents could expand to millions of table cells and exhaust memory

| | |
| --- | --- |
| Severity | Medium |
| CVSS 4.0 | `CVSS:4.0/AV:L/AC:L/AT:N/PR:N/UI:P/VC:N/VI:N/VA:H/SC:N/SI:N/SA:L` (6.8) |
| CWE | CWE-770: Allocation of Resources Without Limits or Throttling |
| Component | `crates/core` (rendering) |
| Status | Fixed in #6 (`9afbd39`) |

- **Description:** Some Markdown constructs expand to far more syntax tree
  nodes than the document has bytes. Tables with short rows are the main
  example, because every row is filled up to the width of the header. The
  renderer limited the input size but not the size of the syntax tree.
- **Impact:** An 80 KB document needed 5.9 GB of memory. Larger documents
  exhaust memory and crash the app, which can lose unsaved text in other
  windows. Memory pressure also slows down other applications.
- **Fix:** The syntax tree is limited to 2,000,000 nodes. Parsing stops as
  soon as the limit is reached, so memory stays bounded while parsing, too.
  The worst accepted document needs about 0.9 GB.
- **Regression tests:**
  - `node_limit_is_exact`, `parsing_stops_soon_after_node_limit` and
    `rejects_documents_above_node_limit` in `crates/core/src/lib.rs`.
  - `many_tables_with_short_rows_are_rejected_quickly` and
    `prose_up_to_the_size_limit_is_accepted` in `crates/core/tests/limits.rs`.
  - FFI and Swift tests for the new error.

### SR-2026-002: Escaping long text and attribute values took quadratic time

| | |
| --- | --- |
| Severity | Medium |
| CVSS 4.0 | `CVSS:4.0/AV:L/AC:L/AT:N/PR:N/UI:P/VC:N/VI:N/VA:L/SC:N/SI:N/SA:N` (4.8) |
| CWE | CWE-407: Inefficient Algorithmic Complexity |
| Component | `crates/core` (sanitization) |
| Status | Fixed in #7 (`7dee443`) |

- **Description:** When the sanitized HTML was serialized, escaping a text
  node or attribute value took time proportional to the number of `&` and
  U+0080 to U+00BF characters times the length of the node. Long paragraphs,
  code blocks, link targets, titles and image descriptions full of such
  characters took quadratic time.
- **Impact:** Ordinary content triggered it as well: a 1.4 MB code block with
  `&&` needed 8.7 s, and 4 MiB inputs needed 83 to 287 s. The editor stays
  responsive because rendering runs in the background, so availability
  impact is rated low: only the preview is affected.
- **Fix:**
  - Long runs of such text are split into separate text nodes before
    sanitization. A property test shows that the output does not change.
  - Attribute values whose escaping would be excessively expensive are
    removed.
  - Time is now linear in the input size.
- **Regression tests:**
  - Unit and property tests in `crates/core/src/sanitize.rs`.
  - `long_code_block_with_many_ampersands`,
    `long_paragraph_with_many_latin1_symbols`,
    `long_link_destination_with_many_ampersands` and
    `long_link_title_with_many_ampersands` in `crates/core/tests/limits.rs`.
    All four fail against the previous code.

### SR-2026-003: Large ordinary documents needed up to 4 GB of memory

| | |
| --- | --- |
| Severity | Medium |
| CVSS 4.0 | `CVSS:4.0/AV:L/AC:L/AT:N/PR:N/UI:P/VC:N/VI:N/VA:L/SC:N/SI:N/SA:N` (4.8) |
| CWE | CWE-770: Allocation of Resources Without Limits or Throttling |
| Component | `crates/core` (rendering) |
| Status | Fixed in #6 (`9afbd39`) |

- **Description:** Dense documents up to the 10 MiB input limit, such as
  one-character list items or emphasis, produced up to 13 million syntax
  tree nodes and needed 2 to 4 GB of memory.
- **Impact:** Heavy memory pressure while such a document is open.
- **Fix:** The node limit of SR-2026-001 bounds memory to about 1.2 GB.
  Dense documents above the limit are rejected after at most 0.3 s with a
  clear error. 10 MiB of prose stays accepted.
- **Regression tests:** The same tests as SR-2026-001, and dense inputs in
  `tests/limits.rs`.

## 7. Accepted risks

| Risk | Justification | Review again |
| --- | --- | --- |
| The worst accepted document needs about 1.2 GB of memory | Needed to render realistic documents up to 10 MiB; bounded and far below what crashes the app | Before v1.0 |
| Fuzzing does not find performance problems | At 64 KB per input, superlinear behavior stays too fast to notice. Dedicated limit tests cover every known expensive construct, and fuzzing now fails on any input slower than 10 s | Every full review |
| Relative links pass the sanitizer, including odd ones such as `java%09script:` | They are not schemes and cannot run code. The preview must resolve them and allow only `http`, `https` and `mailto` (WEB-3) | With the preview (v0.1) |
| CI runner images follow GitHub's labels | Maintained and patched by GitHub; pinning would delay security updates | Before v1.0 |
| Special files (named pipes, devices) in the open dialog are not tested | The user would have to choose one explicitly; the system document architecture reads only regular files | With the folder tree (v0.3), where files are listed automatically |

## 8. Summary

The Rust core and the macOS app skeleton meet the checklist, except for the
preview items, which follow with the preview.

- **Findings:** three, all medium, all fixed with regression tests. No
  finding is open.
- **Hardening during the review:**
  - The repository now enforces SHA-pinned Actions and allows only selected
    Actions.
  - Pull requests from external contributors need approval before CI runs.
  - CI jobs have timeouts; the nightly toolchain and the CI tools are
    pinned.
  - Fuzzing reports slow inputs.
  - The app verification needs no Python.
  - The README documents autosave and versions.
- **Open item:**
  - CI-7 (CodeQL for Swift) is fixed together with the preview in v0.1.
- **Recommendations for the next review (end of v0.1):**
  - Concentrate on the preview: WEB-1 to WEB-5, threats S1, I1, I3, E2 and
    E3, and link resolution (attack 5).
  - Check that rendering runs at most once at a time (D4).
