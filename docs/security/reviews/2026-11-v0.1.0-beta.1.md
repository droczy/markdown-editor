## 1. Scope

- **Components reviewed:** the whole project at the reviewed commit, with
  emphasis on everything added since the previous review:
  - The editor (`NSTextView`) and the preview (locked-down `WKWebView`).
  - Clicked links: decided by the core (`link_action`), copied to the
    clipboard, never opened; the notice and the one-time explanation.
  - Task checkboxes in the preview that change the document (`toggle_task`,
    per-page token).
  - The network entitlement that WebKit requires.
  - The release workflow, the SBOM and the attestations.
- **Changes since the previous review:** #11 (CodeQL for Swift), #12
  (editor and preview), #14 (task checkboxes), #15 (zizmor, nightly
  advisories), #16 (links are copied), #17 (no window tabs), and the pull
  requests of this review: #18 (task checkbox click area), #19 (UI tests),
  #20 (release workflow), #21 (SR-2026-004), #22 (SR-2026-005), #23
  (feature list) and #24 (nightly mutation testing).
- **Out of scope:**
  - Local images (v0.2), the folder tree (v0.3), LaTeX (v0.4), Mermaid
    (v0.5) and the Linux app.
  - Distribution to other users: the app is ad-hoc signed and not
    notarized, which is enough for the maintainer's own use (see accepted
    risks).

## 2. Threat model

Changes to the [threat model](../threat-model.md):

- System overview and data flow diagram: the preview is in place; clicked
  links leave the app only through the clipboard; task clicks flow back
  from the preview to the editor; releases are built by the release
  workflow.
- T4 (release artifacts replaced or modified): in place with the release
  workflow, signed tags, attestations and immutable releases.
- E5 (CI compromise): covers the release workflow, whose triggers need
  write access.
- D1 (resource exhaustion): the editor uses TextKit 1 (SR-2026-004), and
  the node limit also bounds the preview's memory (SR-2026-005).
- T5 (task clicks), T6 (clipboard), I1 (network entitlement) and E3 (no
  links opened) were added with #12, #14 and #16 and verified in this
  review.
- Residual risks: the ad-hoc signed release and the memory of the largest
  accepted documents.

## 6. Findings

Both findings were found and fixed during this review. Exploitation needs
a user who opens a crafted document; ordinary documents can trigger
SR-2026-004 as well. No released version was affected.

### SR-2026-004: Long paragraphs made the editor unresponsive for minutes

| | |
| --- | --- |
| Severity | Medium |
| CVSS 4.0 | `CVSS:4.0/AV:L/AC:L/AT:N/PR:N/UI:P/VC:N/VI:N/VA:H/SC:N/SI:N/SA:L` (6.8) |
| CWE | CWE-407: Inefficient Algorithmic Complexity |
| Component | `apps/macos` (editor) |
| Status | Fixed in #21 (`e08e2ee`) |

- **Description:** The editor used TextKit 2, which lays out and draws
  each paragraph as a whole. Its cost grew much faster than the length of
  the paragraph: one keystroke in a paragraph of 1.6 million characters
  took 10.6 s.
- **Impact:** A document with a paragraph of a few megabytes, such as data
  without line breaks or an embedded Base64 image, made the whole app
  unresponsive for minutes while its memory grew past 4 GB. Unsaved text
  in other windows was at risk if the user had to force the app to quit.
- **Fix:** The editor uses TextKit 1 with non-contiguous layout. A 6.3 MB
  paragraph opens within a few seconds, and typing in it is immediate.
- **Regression tests:**
  - `configuration` (the editor uses TextKit 1 with non-contiguous layout)
    and `longParagraph` (2.1 million characters open and take a keystroke
    within 3 s) in `PreviewComponentTests.swift`.
  - `testFileWithoutLineBreaksCanBeEdited` in `DocumentFileTests.swift`:
    opens a 6.3 MB file without line breaks, types and saves within 60 s
    (267 s before the fix).

### SR-2026-005: The preview needed up to 3.4 GB for documents of a few megabytes

| | |
| --- | --- |
| Severity | Medium |
| CVSS 4.0 | `CVSS:4.0/AV:L/AC:L/AT:N/PR:N/UI:P/VC:N/VI:N/VA:L/SC:N/SI:N/SA:L` (4.8) |
| CWE | CWE-770: Allocation of Resources Without Limits or Throttling |
| Component | `crates/core` (node limit), preview |
| Status | Fixed in #22 (`a412229`) |

- **Description:** The node limit of 2,000,000 bounded the core's memory,
  but the preview's web engine needs up to about 2 KB per node, far more
  than the core.
- **Impact:** Documents of 2 to 3 MB within the limit made the preview use
  up to 3.4 GB in addition to 0.8 GB in the app. The app stayed
  responsive, but the Mac came under memory pressure.
- **Fix:** The node limit is 1,000,000. The worst accepted documents need
  about 1.8 GB in the preview and 0.5 GB in the app. Real documents have
  50 to 80 nodes per KiB and stay below the limit up to the size limit of
  10 MiB.
- **Regression test:** `long_tables_and_many_paragraphs_are_rejected` in
  `crates/core/tests/limits.rs`; `prose_up_to_the_size_limit_is_accepted`
  still passes.

## 7. Accepted risks

| Risk | Justification | Review again |
| --- | --- | --- |
| The worst accepted document needs about 2.3 GB: 1.8 GB in the preview's web process and 0.5 GB in the app | Bounded by the node limit; the preview runs in a separate process and the app stays responsive; lowering the limit further would reject real documents | Before v1.0 |
| A 50 MB file in a single line takes about 13 s and 2.2 GB to open | Bounded by the file limit; typing is immediate afterwards; such files are rare and the user chooses to open them | Before v1.0 |
| The release is ad-hoc signed and not notarized, so macOS asks before the first start of a downloaded copy | Enough for the maintainer's own use; the checksums and the attestations signed by GitHub prove where the files come from | Before the app is offered to other users |
| A `mailto` link can contain an encoded `@`, so the copied address has two (attack 12) | Nothing is hidden: the notice shows the whole copied text; any email link can name an address of the author's choice | With the next change to links |

The accepted risks of the previous review still apply, except the one on
relative links: the preview resolves them and allows only `http`, `https`
and `mailto` (WEB-3).

## 8. Summary

The editor, the preview, the link and task handling and the release process
meet the checklist.

- **Findings:** two, both medium, both fixed with regression tests before
  the beta. No finding is open.
- **Fixed during the review, without a finding:** task checkboxes could not
  be clicked on macOS 27, because the link next to the checkbox was only
  one pixel wide (#18).
- **Hardening during the review:** release notes must have a *Known issues*
  section; GitHub's immutable releases are enabled.
- **Observations:**
  - UI tests report runtime warnings about priority inversions
    (`[Internal]`). They occur inside the UI test automation's own steps
    and have no frame in the app's code; no action.
  - The preview reloads the page without limit when WebKit's content
    process ends. No crash was seen even above 3 GB; a limit on reloads is
    recommended as hardening.
- **Recommendations for the next review (end of v0.2):**
  - Local images: path confinement (FILE-4) and threat I2.
  - Measure TextKit 2 again with each macOS release.
  - Limit reloads after the web content process ends.
